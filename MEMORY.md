This meant `header`/`footer` never actually reached 672px; they collapsed to exactly their content's width, so `justify-between` had zero slack and items touched (0px gap). Latent since Phase 1 but invisible until Step 4 added a 2nd header child (`<nav>`) for `justify-between` to actually operate on. **Fix:** add `w-full` (explicit `width: 100%`, capped by `max-width`) so `width` is no longer `auto` — this sidesteps the stretch/auto-margin conflict. **Rule going forward: any direct child of `<body>` using `mx-auto max-w-2xl` needs `w-full` too, since `<body>` is a flex column.** Also added a `flex-col`/`sm:flex-row` responsive stack to `Header.astro` — separately, the full wordmark + 3 nav links don't fit in ~327px of mobile width with any gap, which is a content-density issue, not the same bug.

- **2026-07-31 — Security pass: CSP headers generated at build time, not hand-written.** Astro inlines small hoisted `<script>` tags directly into the HTML (not as external files with `src`) — confirmed by inspecting `dist/*.html`: the dark-mode bootstrap script in `BaseLayout.astro`, `ThemeToggle.astro`'s click handler, and the Writing page's category-filter script all end up as literal inline `<script>` bodies, each with different content per script (and the exact minified bytes can shift on any unrelated build). A `Content-Security-Policy` with `script-src 'self'` alone would silently break all three (browser blocks inline scripts with no error dialog, just a console warning) unless every current inline script's exact SHA-256 hash is listed — and hand-maintaining that list would drift out of sync the moment any of those three files changes. Solution: `scripts/generate-headers.mjs` runs as `postbuild` (after `astro build`), scans every `dist/**/*.html` for inline `<script>` tags (regex excludes ones with a `src` attribute), computes `sha256-` hashes of their *exact, untrimmed* text content (CSP hashes the literal text node — trimming whitespace before hashing produces a hash that won't match what the browser computes, learned by testing: an early version `.trim()`'d before hashing and computed a different hash than the actual served content), and writes `dist/_headers` (Cloudflare Pages' custom-headers file) with those hashes injected into the CSP's `script-src`. This means `dist/_headers` is **never hand-edited or committed** — it's fully regenerated by every `npm run build`, so it can never go stale relative to the actual inline scripts. Also sets `style-src 'self' 'unsafe-inline'` (Astro's scoped component styles are inlined as `<style>` tags too, but they differ *per page*, so hash-locking them isn't practical the way the finite set of scripts is — style-injection risk is much lower than script XSS, so `unsafe-inline` there is an accepted tradeoff), plus `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`, `Permissions-Policy`, and `Strict-Transport-Security` (HSTS `max-age=31536000; includeSubDomains`, deliberately **without** `preload` — the site is still on the `.pages.dev` subdomain, not a custom domain yet, and HSTS preload-list submission is very slow to reverse; add `preload` only after a custom domain is settled and the human explicitly wants it). Verified by serving `dist/` locally with the generated headers attached and loading it in a real browser: dark-mode toggle and the Writing category filter both function with zero CSP console errors. Also added `.github/dependabot.yml` (weekly `npm` update PRs) and confirmed via `git log --all -p` grep that no real secrets have ever been committed (only a docs placeholder `"change-me"` password and env-var *names*, never values) — `npm audit` is clean (0 vulnerabilities).

Chose path-based branching in `Footer.astro` itself over threading a prop through every page/layout — cheaper, and `Footer` already renders identically everywhere so it's the one place that needs to know. `PostLayout`'s own end-of-post form keeps its explicit override ("Enjoyed this? ...") rather than inheriting the Footer's logic, since it already has stronger context (you just finished reading a post) than a URL-prefix guess could give it. This means the dashboard's "Accent color"/"Body font"/"Accent font" fields (seen in the Archives-page screenshots) are themselves just setting these same variables, and a "Custom CSS" override (if unlocked on the human's plan — unconfirmed pricing tier, they're checking) only needs a handful of lines, not a full stylesheet: override `--font-accent`/`--font-body` with websafe stand-ins for Newsreader/Inter (no web fonts in email), and add a `blockquote { border-left: 4px solid var(--color-accent); font-style: normal; }` rule, since Classic's default blockquote (italic, no border) is the opposite of this site's own (`not-italic`, left accent border, see `PostLayout.astro`'s `prose-blockquote:*` classes). - **2026-08-10 — Built `npm run now` (`scripts/now-cli.ts`), an interactive CLI for editing the Now page. Dev-only tooling, never runs during `npm run build`/deploy.** Human wanted a prompt-driven way to update `src/content/now/` instead of hand-editing YAML frontmatter (which had produced real mistakes — see the "formatting mistakes" review earlier this same day: comma-crammed array items, unrendered Markdown-link syntax, unfilled template placeholders left live). Three deliberate design choices, all confirmed with the human before building (not assumed):
  1. **Writes a new dated snapshot file (`YYYY-MM-DD.md`) instead of overwriting `current.md`.** The `now` collection's loader already globs every `*.md` in the folder and both `now.astro`/`index.astro` pick whichever has the newest `updatedAt` — multiple dated files was already how the architecture was designed to work, just unused until now. Same-day re-runs overwrite that day's file (with a confirm prompt); different days always create a new file. `current.md` itself is untouched/still valid — no forced migration.
  2. **`@inquirer/prompts` + `yaml` (new devDependencies, dev-only, never ship in `dist/`)** over hand-rolled `readline` — nicer UX (inline defaults, y/n confirms) for little code. **`npm install` initially pulled in 4 vulnerable transitive deps (fast-uri, js-yaml, nanoid, postcss — 3 high, 1 moderate); `npm audit fix` resolved all 4 with non-breaking patch bumps, re-verified with a clean build afterward.** Also added `tsx` as a devDependency to run the CLI (`scripts/now-cli.ts`) — deliberately did NOT rely on Node's native `.ts` type-stripping (confirmed working on the installed Node v26, but package.json's stated minimum is only `>=22.12.0`, and native stripping's availability-without-a-flag across that exact version range wasn't confirmed) — `tsx` sidesteps the whole question.
  3. **Link support on every field, not just `watching`** — reuses `parseInlineLinks`/the `[text](url)` convention from `src/lib/utils.ts` (built earlier the same day for `now.astro`'s rendering). The CLI's `toEditable()`/`composeValue()` round-trip a value through that same parser so editing an existing linked item shows its plain text + URL separately instead of raw `[text](url)` syntax as the edit default.
  - **Schema extracted to `src/content/now.schema.ts`** so the CLI validates against the *actual* schema `content.config.ts` uses, not a hand-copied duplicate that could drift. **Gotcha: `content.config.ts` imports `defineCollection` from `astro:content`, a Vite-injected virtual module that does not exist outside Astro's own build/dev pipeline** — a plain Node/tsx script importing `content.config.ts` directly would crash. The schema itself only needs `astro/zod` (a real package subpath, not a virtual module), so pulling just the `z.object({...})` out into its own file made it safely importable from both sides.
  - **Second, near-identical gotcha hit in `src/lib/utils.ts`:** its dev-time `console.assert()` self-tests are gated on `import.meta.env.DEV` — also Vite-injected, also `undefined` outside Astro's pipeline, and this file (via `parseInlineLinks`) *does* need to be imported by the CLI. Fixed with `import.meta.env?.DEV` (optional chaining) rather than splitting the file — one-line fix, doesn't change site behavior at all since Vite always provides `import.meta.env` there.
  - **`@inquirer/prompts` cannot be driven by piped/redirected stdin at all — confirmed by direct testing, not assumed.** `input()` accepts a piped default-accepting blank line fine, but `confirm()` throws `ExitPromptError: User force closed the prompt` immediately, even with 40+ blank lines already sitting in a real file redirected via `<`stdin (ruled out a pipe-timing race specifically to confirm this). It needs a real TTY. **This means I (the agent) cannot fully drive/test the live interactive flow myself in this sandboxed tool-execution environment** — instead exported the pure-logic helpers (`splitFrontmatter`, `loadLatestEntry`, `toEditable`, `composeValue`) from `now-cli.ts`, guarded behind `if (process.argv[1] === fileURLToPath(import.meta.url))` so importing the module for testing doesn't also trigger `main()`'s prompts, and verified file-discovery/latest-picking, link round-tripping, schema validation, and YAML-output-then-reparse-then-schema-revalidate all directly via function calls (all passed). **The human still needs to run `npm run now` themselves once for the first real end-to-end confirmation of the actual prompt UX** — told them this plainly rather than claiming full verification I didn't actually have.
  - **YAML output style tuned to match the hand-authored convention:** `yaml.stringify(data, { defaultKeyType: 'PLAIN', defaultStringType: 'QUOTE_DOUBLE', lineWidth: 0 })` — without `defaultKeyType: 'PLAIN'`, it was also double-quoting object *keys* (`"updatedAt":` instead of `updatedAt:`), caught by inspecting actual test output rather than assuming the first working option was also stylistically correct.
  - **`specs/content-guide.md`'s quick-reference table previously said `now/` is "always exactly one 'current' file" — no longer true**, updated to describe the newest-`updatedAt`-wins convention and point at `npm run now`.
